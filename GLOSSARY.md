# Context & Glossary (guito-ui)

- **Expense occurrence** — the purchase instant (`bookingDate`), distinct from creation/update audit dates. Editable Date/Time use Europe/Lisbon; new expenses default to now, not historical-import midnight. Known offset prefills retain their instant; DST gaps/folds are validated (ADR 0014).
- **Expense ID** — immutable positive numeric Int32 backend identity, distinct from the bank transaction Int64 identity normalized to text. Digit-only legacy strings adapt at the HTTP boundary; missing/invalid IDs remain null and cannot open an editor. List position, description and `storedOrder` never identify an expense or a reconciliation reference.
- **Expense revision** — API decimal Int64 revision string with a strong quoted ETag. Edit/delete send the received ETag unchanged as `If-Match`; a stale token yields 412.
- **Uncertain mutation outcome** — a timeout, lost response or 5xx after a write. Exact-ID readback establishes current state only. Original intent/revision stays separate; renewed writes require deliberate reload/review. See [issue #70 contract](docs/issue70-edit-delete-expenses.md).
- **Edit Expense canonical frames** — approved mobile `3359:570`, desktop `3359:644`, recovery gallery `3361:681`, interaction contract `3362:1189`; approval comment `6167052038`.
- **Create Expense canonical frames** — approved mobile `3094:35`, desktop `3094:9704`, validation `3094:9937`, save failure `3094:10011`, voice prefill `3134:10053`; native Time shares the Date row (ADR 0014).

- **Guito design file** — José's duplicate of the "Simple Design System (Community)" Figma file, key `UoIK5MnIqDrgfHqMmBZoYk` (owner José). The Community original is read-only source and never edited. App designs live on its dedicated **Guito App** page. See ADR 0010.
- **Design loop** — the UI workflow: Hermes drafts a screen on the Guito App page via the Figma MCP → José validates/edits in Figma → approval becomes the implement source. Design changes happen in Figma, never as code-side drift.
- **Token sync (MCP)** — the process writing `design/tokens.json` from the design file's 'Color' variables (SDS Light mode), read via the Figma MCP (see ADR 0010). The REST/pull path is impossible on this plan: `file_variables:read` is Enterprise-only. The role→variable mapping lives in `tools/tokens/figma.json`.
- **User flow board** — the FigJam "Guito User Flow" (https://www.figma.com/board/TulG8ptcGlLxQI78GciXr3): the interaction contract (auth gate → Sign In → Expenses List → Create Expense, sign-out via header avatar). Linked from the Guito App page. Decisions recorded in ADR 0011.
- **Sign In frames** — mobile (`node-id=3071-35`) and desktop (`node-id=3080-53`) frames on the Guito App page, drawn to the minimalist, Google-only direction (centered logo/tagline/button with the Google G mark, bottom trust line). Pending José's approval; approval makes them the implement source for the Sign In screen and the route guard.
- **Bank review inbox** — review surface for all imported bank transactions. Initial filter All; every row starts collapsed. Click/Enter/Space toggles one inline expansion. #134 adds canonical booking-day groups, explicit Match/Unmatch, desktop side-by-side contextual history and state-preserving mobile Transactions/Expenses views. See [the current contract](docs/issue134-manual-matching.md).
- **Review state** — `needsReview`, `matched`, or `ignored`; independent of the bank booking status (`BOOK`). A suggested category is not a match. Ignore and Return to review are reversible without confirmation.
- **Linked expense** — the durable numeric-ID Expense attached to a matched Bank Transaction. Match explicitly selects an eligible server suggestion; Unmatch sends the expected current Expense ID. Neither changes or deletes the Expense. Atomic create-and-match uses a persisted UUID and immutable historical receipt (#135).
- **Suggested Expense** — an eligible candidate supplied by the API for the expanded Transaction, never inferred from loaded Expense history. A suggestion/count is not a confirmed match or evidence an Expense is absent.
- **Contextual Expense history** — read-only occurrence-ordered paged history including linked and unlinked Expenses. Matched uses all known Bank links; Suggested uses the current expanded Transaction's candidates. Offset pages are live, not a snapshot.
- **Bank frames** — #134 approved desktop `3522:1235`, mobile initial `3565:1712`, candidates `3512:1019`, empty `3512:1128`, linked `3512:1205`, history `3565:1788` in the owner file. Supersedes ADR-0015's #133 composition; see the current matching contract for links and safety restrictions.
- **Needs-review bank transaction** — an imported row requiring review, not evidence that an expense is absent. Bank IDs remain strings internally to preserve Int64 identity. Create opens the canonical existing editable Create Expense page with exact positive Int64 text context; Save uses only the atomic Bank endpoint (#135).

- **Create-and-match operation** — one frozen ExpenseCreate payload plus UUID retained in sessionStorage before POST. An uncertain response requires receipt lookup; lookup 404 does not prove rollback. Only deliberate retry may send the same payload/UUID after another lookup.
- **Create-and-match receipt** — immutable historical completion evidence, not current Bank link state. Acknowledgement returns to authoritative Bank refresh and never replays or relinks after Unmatch. See [#135](docs/issue135-create-and-match.md).
